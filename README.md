# 커피 주문 시스템

포인트로 결제하는 커피 주문 API입니다. 메뉴 조회, 인기 메뉴 조회, 포인트 충전, 주문 네 가지를 제공합니다.

기능 수를 늘리는 대신 **같은 자원에 요청이 겹칠 때 데이터가 어떻게 되는지**에 시간을 썼습니다.

* **동시 요청 정합성** — 잔액과 재고를 비관적 락으로 직렬화
* **데이터 일관성** — 멱등키로 중복 요청 차단, 포인트 원장과 잔액 대조
* **다수 인스턴스** — 정합성 판단을 JVM이 아니라 DB에 둠

## 기술 스택

| 항목 | 버전 |
|---|---|
| Java | 17 |
| Spring Boot | 4.1.1 |
| MySQL | 9.7 (Docker) |
| springdoc-openapi | 3.1.0 |

## 실행 방법

```bash
docker compose up -d     # MySQL 9.7, 호스트 13306 포트
./gradlew bootRun        # http://localhost:8080
./gradlew test           # compose가 떠 있어야 합니다
```

* compose가 `coffee`(실행용)와 `coffee_test`(테스트용) 두 스키마를 만듭니다.
* `ddl-auto: create`라 **띄울 때마다 테이블이 다시 만들어지고 시드가 들어갑니다.** 사용자 3명, 메뉴 10개, 주문 15건입니다.
* 테스트를 별도 스키마로 분리한 이유는 `@SpringBootTest`도 `ddl-auto: create`를 실행해 떠 있는 앱의 테이블을 날리기 때문입니다.
* API 문서는 `/swagger-ui/index.html`에 있습니다.

## API

모든 응답은 `{ "code", "message", "data" }`로 감쌉니다.

| 메서드 | 경로 | 설명 | Idempotency-Key | 성공 |
|---|---|---|---|---|
| GET | `/api/menus` | 메뉴 목록. 재고 0이면 `SOLD_OUT` | 불필요 | 200 |
| GET | `/api/menus/popular` | 최근 7일 인기 메뉴 3개 | 불필요 | 200 |
| POST | `/api/points/charge` | 포인트 충전 | **필수** | 200 |
| POST | `/api/orders` | 주문. 여러 메뉴·수량 가능 | **필수** | 201 (재요청 200) |

```http
POST /api/orders
Idempotency-Key: 3f1c2b9e-...

{ "userId": 1, "items": [ { "menuId": 1, "quantity": 2 }, { "menuId": 2, "quantity": 1 } ] }
```

| 상태 | code | 언제 |
|---|---|---|
| 400 | `MISSING_IDEMPOTENCY_KEY` | 멱등키 헤더 없음 |
| 400 | `INVALID_REQUEST` | 필드 검증 실패, 빈 키, 100자 초과 |
| 400 | `INVALID_ORDER_ITEMS` | 같은 메뉴를 두 항목으로 나눠 보냄 |
| 409 | `INSUFFICIENT_POINT` / `INSUFFICIENT_STOCK` | 잔액·재고 부족 |
| 409 | `IDEMPOTENCY_KEY_CONFLICT` | 같은 키에 다른 본문 |
| 503 | `LOCK_TIMEOUT` | 락 대기 3초 초과 |

## 설계 의도와 근거

### 조회 - 인기 메뉴의 "최근 7일"

요구사항 한 줄("최근 7일간 인기 있는 메뉴 3개")에서 정해야 할 것이 네 개였습니다.

| 정할 것 | 정한 것 | 이유 |
|---|---|---|
| 7일의 기준점 | 조회 시점부터 168시간 전까지 롤링 | 자정으로 끊으면 "오늘"이 타임존에 묶입니다. 시점 비교면 인스턴스 시간대가 달라도 결과가 같습니다 |
| 1회의 단위 | **주문 항목 수.** 수량은 안 셉니다 | 10잔짜리 주문 하나가 순위를 뒤집지 않게 |
| 동률 | 메뉴 ID 오름차순 | 순위를 결정적으로 만드는 장치 |
| 3건 미만 | 있는 만큼, 0건이면 빈 배열 | 오류가 아닙니다 |

```sql
SELECT new ...PopularMenuRow(m, COUNT(oi.id))
FROM OrderItem oi JOIN oi.menu m JOIN oi.order o
WHERE o.createdAt >= :from          -- now - 168h
GROUP BY m
ORDER BY COUNT(oi.id) DESC, m.id ASC
```

* **`OrderItem` 한 행 = 그 메뉴가 포함된 주문 1회.** 같은 메뉴를 여러 항목으로 쪼개는 것을 `INVALID_ORDER_ITEMS`로 막기 때문에 성립합니다.
* **주문 상태 필터가 없습니다.** 취소가 범위 밖이고 실패 주문은 롤백되어 행이 안 남으므로, `orders`에 있는 것은 전부 성공한 주문입니다.
* **`menus`에 누적 주문 수 컬럼을 두지 않았습니다.** 누적값으로는 "최근 7일"을 좁힐 수 없고, 그 컬럼은 인기 메뉴 한 행에 쓰기가 몰려 주문 경로에 경합을 하나 더 만듭니다.
* **캐시는 보류입니다.** 최신성 요구가 낮은 건 캐시의 허용 조건일 뿐이고, 효과가 있으려면 TTL 안에 조회가 반복돼야 합니다. 인덱스로 해결되는 범위를 먼저 측정합니다.

### 충전 - 잔액은 비관적 락으로 잠급니다

* **문제**: 충전은 읽은 값에 더해서 다시 쓰는 연산입니다. 일반 `SELECT`는 행을 잠그지 않아 두 요청이 같은 잔액을 읽고 덮어쓰면 한쪽이 사라집니다. 트랜잭션만으로는 안 막힙니다. 각자의 트랜잭션 안에서는 어긋난 것이 없기 때문입니다.
* **선택**: `users`와 `menus`를 `SELECT ... FOR UPDATE`(JPA `@Lock(PESSIMISTIC_WRITE)`)로 잠급니다.
* **낙관적 락을 쓰지 않은 이유**: 경합이 사용자 한 행과 인기 메뉴 한 행에 집중됩니다. 충돌이 드물다는 전제가 깨지는 자리에서는 재시도 비용이 락 대기 비용보다 커집니다.
* 락이 없으면 실제로 얼마나 사라지는지는 [검증](#검증)에서 숫자로 확인했습니다.

### 충전 - 포인트 이력을 남깁니다

요구사항에는 없지만 `point_histories`를 뒀습니다.

* 포인트는 금전 기록이라 잔액 컬럼만으로는 틀어진 지점을 추적할 수 없습니다.
* `amount`에 부호를 담아두면 **원장 합과 잔액을 대조해 정합성을 검증**할 수 있습니다. 갱신 분실을 재현할 때 이 대조가 원인을 그대로 보여줬습니다.

### 주문 - 잠금 순서를 고정하고 재시도는 두지 않았습니다

주문은 `users` 한 행과 `menus` 여러 행을 잠급니다. 순서가 요청마다 다르면 서로 상대가 쥔 행을 기다려 데드락이 납니다.

* **잠금 순서**: `users` → `menus`, `menus` 안에서는 메뉴 ID 오름차순. 모든 주문이 같은 순서를 쓰면 순환 대기가 생기지 않습니다. 난 뒤에 복구하기보다 예방하는 쪽을 택했습니다.
* 잠그는 조회가 모두 `WHERE id = ?` 단건이라 잠기는 것은 그 행 하나뿐입니다.
* **예방이 닿지 않는 곳이 하나 있습니다.** 같은 멱등키로 동시 요청이 여러 건 들어오면 `orders`의 UNIQUE 인덱스에서 중복 키 처리가 일어나는데, 여기엔 잠금 순서와 무관한 데드락 모드가 있습니다. 이 경우에도 InnoDB가 한쪽을 롤백하고 503이 나가므로 데이터는 깨지지 않습니다.
* **그래서 재시도 루프를 넣지 않았습니다.** 넣으려면 그 경로를 재현하는 테스트가 먼저 있어야 하는데 이번 범위에서 할 수 없었습니다. 검증하지 않은 방어는 동작을 보장하지 못합니다.

### 충전·주문 - 멱등 구현이 서로 다릅니다

| | 충전 | 주문 |
|---|---|---|
| 선조회 위치 | 잠근 **뒤** | 잠그기 **전** |
| 트랜잭션 밖 레이어 | 없음 | `OrderFacade` |

* **갈리는 이유는 잠그는 행의 개수입니다.** 충전은 `users` 한 행만 잠그므로, 잠그고 나서 선조회하면 두 번째 요청이 락에서 기다렸다가 첫 번째가 커밋한 이력을 봅니다. UNIQUE 위반에 도달하지 않아 트랜잭션 밖 레이어가 필요 없습니다.
* 주문은 잠금 순서가 `users` → `menus`인데 멱등 선조회는 `orders`를 읽으므로 잠금보다 앞에 올 수밖에 없습니다. 동시 요청 둘이 모두 선조회를 통과할 수 있고, UNIQUE 위반이 난 트랜잭션 안에서는 재조회를 못 합니다. 그래서 **선조회 + UNIQUE + 본문 비교** 세 겹과 트랜잭션 밖 레이어가 필요합니다.
* `OrderFacade`는 하위 시스템을 묶는 Facade가 아니라 **트랜잭션 밖에서 멱등 재조회를 담당하는 얇은 층**입니다. 도메인 조율은 `OrderService`가 합니다. 재고 차감과 포인트 차감이 같이 롤백되려면 한 트랜잭션 안이어야 하기 때문입니다.

### 공통 - 락 대기 3초, 넘기면 503

* `innodb_lock_wait_timeout=3`을 세션 변수로 겁니다. 기본값 50초는 요청 하나가 커넥션을 50초간 쥔다는 뜻이고 그 사이 풀이 마릅니다.
* `CannotAcquireLockException`을 전역 핸들러가 **503**으로 바꿉니다. 처리하다 실패한 것이 아니라 **락 대기가 정해둔 시간 안에 끝나지 않은 상황**이라고 봤습니다. 핸들러를 넣기 전에 테스트를 먼저 써서 500이 나가는 것을 확인했습니다.
* **재시도할 때는 `Idempotency-Key`를 그대로 유지해야 합니다.** 503을 받은 요청이 실제로는 처리됐을 수 있는데, 키가 같아야 서버가 재요청으로 알아봅니다.
* `Retry-After`는 넣지 않았습니다. 적절한 값을 정하려면 측정이 필요한데 아직 숫자가 없습니다.

![락 대기 3초 초과 시 503](docs/images/lock-timeout-503.png)

### 공통 - 인스턴스 간 정합성은 DB를 기준으로 맞춥니다

JVM 안의 `synchronized`나 `ReentrantLock`을 쓰지 않습니다.

| 지켜야 할 것 | 수단 |
|---|---|
| 잔액·재고 동시 수정 | `SELECT ... FOR UPDATE` (DB 행 잠금) |
| 같은 요청 두 번 처리 | `(user_id, idempotency_key)` UNIQUE (DB 제약) |

* 둘 다 DB에 있으므로 **인스턴스를 몇 개로 띄우든 같은 규칙이 적용됩니다.**
* 분산 락을 얹지 않은 것도 같은 이유입니다. 공유 자원이 전부 DB 안에 있는데 Redis 락을 더하면 락과 데이터의 관리 주체가 갈리고 실패 지점만 늘어납니다.
* **아직 해결되지 않은 자리도 있습니다.** outbox 워커는 인스턴스마다 돌면 중복 전송할 수 있고, 인기 메뉴에 로컬 캐시를 쓰면 인스턴스마다 순위가 달라집니다. 각각 5·7단계에서 다룹니다.
* **실행 설정은 아직 단일 인스턴스 개발용입니다.** `ddl-auto: create`와 시드 자동 주입이라 지금 상태로 두 번째 인스턴스를 띄우면 테이블이 다시 만들어집니다. 여러 개를 띄우는 것은 프로파일을 나눈 뒤 6단계 측정에서 합니다.
* 여기 적은 것은 측정 결과가 아니라 **구조상 어디에 기대고 있는지**입니다.

## 검증

동시성 테스트에는 `@Transactional`을 붙이지 않습니다. 트랜잭션은 스레드를 넘지 않아 롤백 안전망이 동작하지 않고, 붙이면 테스트 스레드가 쥔 락 때문에 재현 자체가 막힙니다.

| 클래스 | 개수 | 무엇을 보는가 |
|---|---|---|
| `OrderFacadeTest` | 9 | 잔액·재고 경합, 전체 롤백, 잠금 순서, 멱등 3종 |
| `PointServiceTest` | 5 | 동시 충전 응답, 100건 뒤 잔액, 멱등 3종 |
| `PointChargeLockTimeoutTest` | 1 | 락 대기 3초 초과 시 503 |
| `CoffeeOrderSystemApplicationTests` | 1 | 컨텍스트 로드 |

```
./gradlew test  →  16 tests, 0 failures
```

**검증은 응답이 아니라 DB 상태로 합니다.** 201이 왔다고 차감이 맞았다고 보지 않고, 테스트 끝에서 잔액·재고·주문 건수를 다시 읽습니다. 동시성 테스트도 예외가 났는지가 아니라 최종 상태가 규칙을 만족하는지를 봅니다.

### 락이 없으면 얼마나 사라지는가

`findByIdForUpdate`를 `findById`로 바꾸고 잔액 0에 1,000원 충전 100건을 동시에 보냈습니다.

| 커넥션 풀 | 기대 잔액 | 실제 잔액 | 반영된 건수 |
|---|---|---|---|
| 10 (기본값) | 100,000 | **11,000** | 11건 |
| 5 | 100,000 | **21,000** | 21건 |

![갱신 분실 - 커넥션 풀 10](docs/images/lost-update-pool10.png)

![갱신 분실 - 커넥션 풀 5](docs/images/lost-update-pool5.png)

풀을 절반으로 줄이니 반영된 건수가 두 배가 됐습니다. 동시에 처리되는 수가 곧 같은 잔액을 함께 읽는 수이기 때문입니다.

```
반영되는 건수 = 전체 건수 ÷ 동시에 겹친 수
```

`point_histories`에는 원인이 그대로 남습니다. 97~100행은 넷 다 21,000을 읽고 넷 다 22,000을 썼습니다. 네 건이 들어갔는데 잔액은 1,000만 올랐습니다.

![이력에 반복된 balance_after](docs/images/lost-update-history.png)

이력은 100건인데 `amount` 합과 `users.point`가 어긋납니다. 대조 쿼리 하나로 잡힙니다.

```sql
SELECT u.point, SUM(ph.amount) FROM users u
LEFT JOIN point_histories ph ON ph.user_id = u.id GROUP BY u.id, u.point;
```

락을 되돌리면 `balance_after`가 1,000씩 올라가 100,000에서 끝납니다.

![락 적용 후 이력](docs/images/lock-applied-history.png)

## 범위에서 제외한 것

위 세 가지에 기여하지 않는 기능은 의식적으로 뺐습니다. 고려하지 않은 것이 아니라 판단해서 뺐습니다.

* 인증·인가, 주문 취소와 환불, PG 연동, 장바구니, 알림 발송
* 메뉴 등록·수정과 재고 보충, 주문·포인트 내역 조회

운영이라면 달라지는 점도 적어둡니다.

* `userId`를 요청 본문이 아니라 인증 주체에서 얻어야 합니다.
* 품절과 판매 중지는 다른 개념인데 메뉴 수정 API가 없어 후자를 걸 수단이 없습니다.
